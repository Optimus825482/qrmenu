# P2 — Minibar Tanımları ve Veri Göçü Uygulama Planı

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Merit OS'a Minibar tanım katmanını (ürün grubu, ürün, setup, otel bazlı oda tipi–setup ataması), oda QR üretimini (HMAC token, SVG/PNG/ZIP, yazdırma şablonu, misafir mesajı) ve otel zimmet havuzunu (giriş, iade, düzeltme, kritik seviye, hareket kaydı) eklemek; canlı `minibarlatest` yedeğini (`minibar_legacy`) tanımlar ve tüm işlem geçmişiyle yeni şemaya idempotent, doğrulama raporlu bir scriptle taşımak.

**Architecture:** Yeni modül `src/modules/minibar` (`server/` servisleri + `server/actions/` Server Action sarmalayıcıları + `ui/` pencereleri). Ürün grubu/ürün/setup **sistem geneli kataloğu**dur (şemada `hotelId` yok) → yazmalar `withAdminTx` ile `hotelId`siz = yalnız SISTEM rolü; oda tipi–setup ataması, oda QR ve havuz **otel kapsamlıdır** → `hotelId` zorunlu. Her yazma P1 deseniyle: `zod → assertCan/withAdminTx → prisma.$transaction → audit → publishDefinition|publish`. Havuz yazmaları satır kilidiyle (`FOR UPDATE`) tek transaction'dadır ve P3/P4'ün kullanacağı `takeFromPool(tx, …)` / `restoreStock(tx, …)` / `addToPoolTx(tx, …)` ilkellerini de sunar (havuzun TEK sahibi `src/modules/minibar/server/pool.ts`'tir). Göç scripti `merit/scripts/migrate-from-minibarlatest/` altında bağımsız bir `tsx` CLI'dır: legacy veritabanını salt-okunur okur, hedefe `legacy_id_map` ile yalnız eksik satırları ekler, `--dry-run` tek transaction'ı geri alır, sonunda `migration-report.md` üretir.

**Tech Stack:** P0/P1/P5 ile aynı (Next.js 16.4, React 19, TS 5.9, Prisma 7.10, zod 4, zustand 5, Vitest 5, Playwright 1.64, pg-boss 12). Mevcut paketler yeniden kullanılır: `qrcode`, `fflate` (ZIP), `sharp` (logo dönüştürme), `pg` (göç scripti legacy okuyucusu), `tsx` (CLI). Yeni paket yok.

**Spec:** `docs/superpowers/specs/2026-10-31-merit-platform-design.md` — §3.2 (minibar veri modeli), §6.1 (tanımlar, oda kontrol listesi kuralı, oda QR), §6.2 (otel zimmet havuzu), §9.1 (olaylar), §10 (iş günü), §11 (`stock.*`, `qr.baseUrl`), §12 (göç eşleme tablosu — yetkili kaynak), §14 P2 satırı, §15 kabul 9; `docs/analiz/2026-10-31-anlayis-notu.md` §3 ve §7 (K2 havuz, K4 tam göç, K5 sadeleştirme); `docs/DEVIR.md` §3–§5.

## Review Focus

1. **Aynı ürün için eşzamanlı havuz hareketleri (iade + iade, iade + kullanım):** `FOR UPDATE` ile sıralanır; toplam talep `remainingQty`'yi aşarsa biri `STOCK_INSUFFICIENT "Havuzda yalnız N adet var"` / `"Stokta N adet var"`; bakiye asla negatif olmaz, `total − used = remaining` korunur, her başarılı işlem tam **bir** hareket satırı yazar → Task 7 testi.
2. **Kullanımdaki ürünü/setup'ı pasife alma veya silme:** aktif bir setup içeriğindeki ürün pasife alınamaz, atanmış veya geçmiş işlemde kullanılmış setup silinemez/pasife alınamaz; ham Prisma hatası yerine hangi setup'ların engellediğini söyleyen Türkçe `CONFLICT` → Task 2 ve Task 3 testleri.
3. **Aynı oda tipine eşzamanlı iki setup ataması / içeriği boş setup:** oda tipi satırı kilitlenir, sonuç iki isteğin birleşimi değil biri **tamamen**; içeriği boş veya pasif setup atanamaz (`VALIDATION`, adlarıyla) → Task 3 testi.
4. **QR yenileme ve legacy 6 haneli token:** yenilemeden sonra eski token çözülmez, onaysız yenileme `CONFLICT`; toplu "Tümü/Eski biçim" modu `confirmInvalidate` olmadan `VALIDATION`; 6 haneli legacy token DB'de çalışmaya devam eder ve `/qr/{token}` yönlendirmesi çalışır → Task 5 testi.
5. **Göçün yarıda kesilip yeniden çalıştırılması ve bozuk legacy verisi:** ikinci çalıştırma 0 yeni satır; `--dry-run` sonrası hedefte tek satır/dosya yok; yetim `setup_icerik`, tekrar eden `setup_icerik`, aynı otelde çift `kat_no`, `toplam − kullanılan ≠ kalan` havuz satırı, geçersiz base64 logo çökme yaratmaz, raporda uyarı olarak çıkar → Task 9, 10, 12, 14 testleri.
